# Living Valley: review-to-release audit

This audit checks the new adventure against the player's completed 24-mission review and the subsequent 104-encounter blueprint supplied in `Pasted text.txt`. It treats the player's observations as evidence of their experience, and the proposed blueprint as the requested design direction. A proposed feature in that discussion is not evidence that it already existed.

The original adventure was completed twice through its public interface before the redesign; those results and the original learning gaps are recorded in [LIVING_VALLEY_PLAYTEST.md](LIVING_VALLEY_PLAYTEST.md). This audit concerns the separate `living-valley/` implementation.

## Blueprint and progression checks

The authored structure exactly follows **92 ordered lessons and 12 chapter bosses**, for **104 playable encounters**, **290 practical steps** and **226 knowledge questions**. Chapter encounter counts are **8, 9, 9, 8, 10, 9, 8, 9, 9, 8, 9, 8**. Each chapter ends in exactly one boss. All prerequisite and reinforcement identifiers resolve to capabilities introduced earlier; no aliases were invented to make that check pass. The practical work uses **eight tool types** and **seven activity kinds**.

The named lessons cover computer literacy, Linux navigation and file handling, accounts and permission policy, processes/services/storage, networking, threats and verification, web trust and cryptography concepts, logs and evidence, bounded scripting, Windows concepts and PowerShell, defensive decisions, and integrated investigation. Linux and Windows are distinguished in Chapter 1, before the dedicated Windows chapter.

The skill journal must be read as a record of encounters and assistance, rather than a certification checklist. A lesson can introduce one concept while independently recalling an earlier method. Reinforcement belongs in the skill tree and journal alongside the encounter's primary skill tags. Completing a discovery encounter does not make all its recalled skills an independent demonstration.

The blueprint's additional supporting-concept list is broader than its 92 named lessons. Implemented examples include DHCP/NAT, CIDR intuition, ARP, SSH awareness, Wi-Fi/VPN boundaries, isolated labs/snapshots, privacy, source reliability and time-zone normalization. Six additional evidence activities in [foundation-details.js](../living-valley/data/foundation-details.js) close the specific supporting-concept gaps found during this audit without adding padded encounters:

| Existing lesson | Added investigation | Scope |
| --- | --- | --- |
| `c02-01`, The Paper Trail | Classify the same delivery as a human note, CSV table or JSON object. | Inspect supplied representations; do not claim to run an importer or convert a file by renaming it. |
| `c04-02`, The Work Crew | Separate application processes from the architecture board's kernel mechanisms. | Distinguish account privilege from user/kernel protection domains; do not claim to inspect a real kernel. |
| `c06-04`, The Poisoned Package | Compare a known maintenance release with a courier's substitute and its self-supplied checksum. | Recommend an approved staged test using supplied provenance records; do not claim to execute an installer or perform real signature verification. |
| `c09-03`, The Command Chain | Compare pseudocode against specific, absent and mismatched approval cases. | Review an algorithm and its failure cases; pseudocode is not executable code. |
| `c09-05`, The Decision Machine | Classify exact allowed relay IDs, empty input and command-like extra text. | Apply a stated allowlist without executing card contents; validation does not replace separating data from code. |
| `c11-05`, The Ranger's Rules | Verify a hosted-notebook request and assign provider/customer duties from the actual agreement. | Introduce zero-trust access reasoning and shared responsibility for this service model; network location alone is not identity, and cloud duties are not universal across products. |

Each addition includes its own question and explanation. These are bounded, practical introductions, not exhaustive networking, operating-system, programming or cloud-security training. Other suggested Linux utilities such as `awk`, `tee`, `diff`, `tar` and `gzip` are not taught as a complete toolkit here. The mission count alone does not establish comprehensive professional coverage.

## Verification performed

An independent `npm run test:valley` run passed **79 of 79 tests** after the complete curriculum could be imported. It executed every canonical encounter and two renamed return-trip variants through the actual runtime, checked wrong answers and evidence gates, round-tripped chapter saves, and verified the original shell's 81 commands and 79 nondecision outcomes. A second run passed all 79 after the return-trip syntax-fading regression and fix were added. A fresh post-integration run also passed all 79 against the frozen 104-encounter, 290-step, 226-question curriculum, including all six supporting-concept additions.

These are functional, authored-route checks. They do not show whether a beginner can discover an unfamiliar solution unaided, whether every plausible command is supported, or whether someone retains a skill weeks later. Browser and phone results belong in their corresponding test artifacts and release report; they should not be inferred from this unit run.

The original hero's SHA-256 remains `3d1106f9a5351d5be64fb1680b31de268e792429c85d35fa1ce48b1f877e277a`, and the caption remains “Every expert starts somewhere.” The root game's source remains separate from this new entry point and save namespace. Office and Night Shift remain in development even after the finale.

## Boundaries that must stay clear

- The shell is a bounded teaching interpreter over fictional state. It does not execute host commands or reach real networks. It is not complete Bash, PowerShell, Linux or Windows.
- POSIX ownership and mode bits are inspected and repaired as policy metadata. The simulation does not enforce full discretionary access control as different real accounts. Administrative operations remain scenario-scoped.
- Report checks require factual anchors and complete fields. They do not perform general natural-language reasoning or grade the quality of every possible explanation.
- Return trips rename evidence and paths while retaining the underlying scenario. They are practice, not a fresh incident generator, an adaptive curriculum or validated spaced-repetition research.
- Illustrated motion, character expressions and optional discovery tones are implemented presentation features. They are not voiced cinematics or continuous ambient audio.
- Automation demonstrates functional routes and regressions. Independent beginner observation, unfamiliar transfer tasks and delayed recall remain necessary evidence for educational effectiveness.

The next review should watch a real player at the original friction points: finding a file before opening it; choosing a filter from the investigation question; explaining a result without repeating a command; transferring that method to a second case; and completing a boss with optional help available but no displayed solution.
